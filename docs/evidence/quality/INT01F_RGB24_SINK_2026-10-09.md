# INT-01F — Bounded RGB24 Sink Handoff

Date: 2026-10-09 WIB
State: Await exact-head Windows CI proof. Draft PR #20; no merge.

## Purpose
The existing image-only scene workflow can import DOCX+Axxx+TXT, render
continuous PNG frames, verify each PNG and decode exact ordered RGB24
scanline blocks. This wave qualifies a **synthetic sink interface**, not
a native encoder process or an MP4.

## Changes
- \`feed_rgb24_to_sink()\` sends packed RGB24 bytes to an injected
  synchronous sink and records an immutable transfer receipt: exact
  frame count, FPS, dimensions, byte count and SHA-256.
- Bounded write fragments of at most 64 KiB; detect zero progress,
  boolean/non-integer, overreported lengths and more than 256 short
  writes per fragment rather than looping forever.
- Cancellation probes occur before starting, between frame blocks
  and between partial writes; callers must discard output on error.
- Frame-level progress callback fires only after a complete frame
  was successfully accepted by the sink.
- No codec availability is claimed. An abstract injected sink could
  be a fake; in this wave tests exclusively use in-process fake sinks.
  No subprocess, FFmpeg binary, UI, MP4 file or packaging is introduced.

## Limitations / required next permissions
This does not enforce wall-clock timeouts if a supplied write call
blocks; only the later separately approved native process runner can
provide process termination and cleanup. Partial sink bytes cannot be
rolled back by this method. The future native transaction must stage
output safely, revalidate canonical sources and inspect the final MP4
codec, frame count and duration before publication.
